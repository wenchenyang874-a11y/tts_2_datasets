## 日常开发

1. 确认真实仓库、当前 main 和已有改动；有未提交改动时先核对，不能硬重置或丢弃。
2. 获取 origin/main 最新提交，干净且仅落后时以 fast-forward 同步；出现分叉时核对双方变化并正常整合，不强制推送。
3. 在 main 完成本次改动和文档维护，完成影响范围所需的验证，然后正常提交、推送。常规开发无需再创建迁移分支；若远程保护要求 PR，遵守保护规则。
4. 保留 Git 历史、已发布 Tag 和 Web 备份。回退可正常 revert，或从 Web 备份建立修复分支；涉及实际用户数据时仍需验证恢复方案。

## 发布边界

直接在 main 开发不等于自动发布。用户于 2026-10-13 调整发布授权：先本地提交、验证和构建安装包，交付用户验证；收到用户对该具体构建的验证通过及明确发布通知后，才创建／推送 Tag、建立 Release 草稿、上传并公开资产。Agent 自测通过不能代替用户验收。

未发布期间继续沿用当前版本号，发布后开始下一版时才递增。用户于 2026-10-14 要求每个获准发布的版本一并设为 Latest；为此取消 GitHub 预发布标记，但 beta 版本号和实际验证边界保留，不宣称未实测的 Windows 10 已通过。稳定版须满足 Windows 10/11 实测门槛。每版最终交付列出实际本地安装包。版本、安装器、验证与发布脚本见 [安装与版本发布](windows-installer-release.md)，系统验证见 [测试记录](../testing/windows-validation.md)。
